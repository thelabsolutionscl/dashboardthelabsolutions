# Monitor Sistema: admin-only pending domain-level authorization

A read-only metadata/name-only inspection of the production Airtable base on September 29 found **26 visible records** in `Monitor Sistema`. This table uses a generic `Name` key and an unrestricted `Notes` text field. Current record names include `MAIL_SIGNATURES`, `MAIL_SENT_ADDRESSES`, `MACHINE_OPS_V3:costConfig`, `MACHINE_OPS_V3:safetyConfig`, `MACHINE_OPS_V3:jobs`, `MACHINE_OPS_V2`, `AGENDA`, `CALENDARIO` and `SIMULACION`. The contents of `Notes` were not retrieved during this inspection. Historical integration docs describe a possible `WATI_CONFIG` record, but that name **was not present** in the inspected snapshot. This mixed design may store sensitive operational configuration alongside routine calendar and machine snapshots.

Simply granting `GET Monitor Sistema` to a signed operator or finance user discloses **all** records and unreviewed JSON in Notes; projecting Airtable field names cannot separate internal configurations from ordinary calendar or operational data because the sensitive values share the same column. Field-level RBAC alone is not sufficient.

The verified Cloudflare Access role matrix therefore classifies the **entire Monitor Sistema table as admin-only** for now. Signed `viewer`, `sales`, `operator` and `finance` receive no list or individual GET, POST, PATCH or DELETE access. Admin retains the exact, canonical Airtable table route; encoded aliases, table IDs, nested paths and general metadata remain subject to the existing fail-closed authorization. This change does not delete, rename, migrate, edit or read the `Notes` value of any record. The current APP_KEY legacy dashboard remains unchanged until Access is configured; this is a staged code protection, **not proof of production enforcement**.

**Required code before final Access cutover:** calendar, agenda, shared-mail, MachineOps and simulation now have narrow dedicated proxy endpoints. The remaining work is to move the other legitimate domain records away from unconstrained `Monitor Sistema` access, with explicit record-name allowlists, verified roles, bounded payload schemas and response redaction. Machine safety/cost configuration and historical `MACHINE_OPS_V2` remain excluded from any blanket non-admin read scope; MachineOps accesses them only through its reviewed route. Until those paths are implemented and real browsers tested, mapping existing full-dashboard users to signed nonadmin roles may disable features that currently depend on generic monitor storage; do not turn on Access without the full integration checks.

See `tests/access-monitor-system-classification.test.js` and security tracking issue #306. The final one-time manual phase still includes proxy DNS restoration, Cloudflare Access/user mapping, external Make/PAT inventory and two-browser tests.
