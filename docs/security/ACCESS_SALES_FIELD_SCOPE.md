# Sales CRM field scope and query safety (September 29, 2026)

The live Airtable schema was inspected in read-only mode. Clientes includes **Datos pago / banco**, historical revenue, overdue invoices and finance links; Cotizaciones includes **Margen real (%)** and unrestricted JSON/proposal fields; Pedidos includes material, labor and total production costs. Row ownership alone is not field authorization.

A signed `sales` identity now receives an explicit, per-table **allowlist of visible Airtable fields**. Both list and single-record GET are projected by the proxy *after* verifying the row's Vendedor. List requests also send only approved `fields[]` to Airtable, plus the mandatory Vendedor field. New Airtable columns are hidden by default rather than exposed automatically. Unreviewed linked-record IDs and attachments are excluded because a row can refer to a client, quote or order owned by another seller. Admin, operator and finance roles are unchanged.

For signed sales users, the only accepted list query parameters are `pageSize`, `maxRecords`, `offset` and optional `fields[]` containing names from that table's approved list. Arbitrary `filterByFormula`, `sort[]` and `view` are blocked: even with response redaction, predicates and result counts can disclose hidden financial fields. The proxy always applies its own server-generated Vendedor filter. Filter/order behavior for sales remains client-side until a server-validated filter DSL is implemented. All returned bodies are newly constructed from approved keys; unexpected upstream fields, row metadata or response metadata never pass through.

**Operational limitation:** the legacy frontend still uses linked-record identifiers in some commercial views. Normal signed sales responses omit relationship IDs. An explicit single-record `?includeVerifiedLinks=1` now returns only same-vendor links checked by the proxy against the independently fetched owner of each referenced row (see `docs/security/ACCESS_SALES_LINKED_RECORDS.md`). The signed `sales` UI cutover still requires adopting/testing this new path; it must not be treated as already wired into the legacy dashboard. Concurrent owner changes by external Airtable writers are not transactionally preventable here.

**Other writers:** Airtable's connected account returned no visible Airtable automations for this base at the time of inspection, but this does *not* establish that Make, direct Airtable editors or other external API clients have stopped modifying owner fields. The independent `ACCESS_SALES_WRITES_ENABLED` switch stays off; coordinate owner-changing writers in the final deployment checklist.

Regression coverage: `tests/access-sales-row-scope.test.js` verifies safe fields, redaction for all three tables and direct record IDs, forbidden projections/formulas/sorts/views, paging and owner checks. The signed sales role remains staged, pending Access configuration and DNS restoration.
